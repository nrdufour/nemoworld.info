People are nervous about apps written by AI. I get it. But the other day I wondered something: was there ever a time when people avoided code because it was written by a *machine* rather than by a person? Not generated by a clever assistant, just generated by a compiler.

There was. And the parallels are closer than the comfortable version of the story admits.

<!--more-->

## The priesthood

When FORTRAN showed up in 1957, John Backus and his team proposed something close to heresy: that you could describe a computation in a language resembling math, and let a program translate it into machine instructions. The reaction from the programmers of the era was not curiosity. It was hostility and derision.

The objection was not stupid. On the machines of the day it was *true*. An early compiler produced code that was slower and larger than what a good programmer could write by hand. Every instruction and every cycle mattered, and the people who had spent years mastering that craft were not wrong to think a machine would waste them.

But alongside the technical objection ran a second one, and that one was pure identity. Real programmers wrote assembly. The folklore went further: the *Story of Mel* celebrated a programmer who refused even symbolic assembly and hand-wrote machine code, and the 1983 essay "Real Programmers Don't Use Pascal" turned the whole thing into a joke. The compiler was not judged, it was *disdained*.

## Two kinds of distrust

Those two objections look the same in conversation and are not the same thing at all.

The first is empirical: *the generated code is worse*. That claim is measurable. You benchmark it, you improve the compiler, and one day the objection simply dies. Which is exactly what happened: as optimizers matured, compiled code caught up with and then passed hand-written assembly for most work, and nobody argues about it anymore.

The second is cultural: *generated code is not real programming*. That one does not die. It goes quiet, changes costumes, and comes back the next time a machine does something a human used to be paid for.

## We have generated code all along

None of this is new, and it was never really about the machine. We have generated code for decades without a second thought. Nobody ever hand-wrote the thousands of lines of marshalling glue that CORBA's IDL compiler, an RPC stub generator, or a WSDL tool produced for them. Doing it by hand would have been the stupid move, and everyone knew it.

CORBA itself was heavy, genuinely heavy, and most of it did not survive the arrival of REST and HTTP. But that was an architecture losing, not a generation technique failing. The glue was never the problem. The mockery was never really about generation either. It was about *which* code the machine is allowed to write.

## The part that never went away

Here the story stops being comforting. A part of the distrust was never resolved and never could be, because it was not about quality.

In 1984, in his Turing Award lecture "Reflections on Trusting Trust", Ken Thompson showed that you cannot verify what a compiler actually emitted. A compiler can hide a backdoor in the code it produces, and hide the mechanism that inserts the backdoor, so deeply that reading every line of source and every line of output will not reveal it. Forty years later, this is still an open problem.

It is not only a thought experiment. In the safety-critical world we *still* refuse to take the compiler on faith. Under standards like DO-178C for avionics, a compiler must be either qualified or its object code verified, because the certified system is not allowed to trust a translation nobody can inspect. The distrust of the compiler never disappeared. It got formalized into a standard.

## What actually separates a compiler from a model

The tidy reply is: a compiler is mechanical, an AI is statistical. I do not think that line holds. A modern optimizing compiler is one of the most complex artifacts we build, and nobody reads the code it emits. It is an oracle we consult, exactly like a model. Miscompilations are real, and they pass the tests.

The real difference is elsewhere, and it is not about mechanism. It is about *specification*.

A compiler's input is a formal language with a defined meaning, so "correct" is a property you can state. An AI's input is natural language, and its output has no formal spec, so "correct" collapses into tests plus human judgment, which is a strictly weaker oracle.

The shape of the failure differs too, and that changes the economics of checking it. A compiler's bugs are rare, local, and roughly independent of what your program means, so you can sample-test and move on. A model's errors are dense and correlated with difficulty: it fails most on the patterns rarest in its training data, which is precisely where you cannot sample, and you have to look at everything.

The failure mode moves, as well. A couple of years ago the complaints were syntax errors and invented APIs. Today they are plausible-but-wrong architecture, logic that is subtly off, and a configuration file hallucinated with perfect confidence. The distrust is not wrong. It is just aimed at the wrong thing.

## The lag

We remember "AI code is buggy" from not that long ago, and it was true not that long ago. That is the worst kind of belief to hold: recent enough to feel like evidence, old enough to be out of date, exactly like "compilers produce worse code" was for a decade after it stopped being true.

It sticks because of an asymmetry. A bad result confirms the prior ("see, still broken"). A good result gets reassigned to the human who reviewed it ("sure, but I cleaned it up"). You can never win the argument, because the argument is not being decided by evidence.

I have watched this cycle repeat at least once or twice in my own lifetime. I remember saying, around the time of Java 1.1, that code generation was the future, and getting laughed at for it. The tools I was pointing at were clumsy, and most of them died. The direction was right anyway.

## The most dangerous thought

I am not the first to notice this. Bret Victor made almost the same argument in 2013, in a talk called "The Future of Programming", delivered in character as a programmer from 1973. He opens on the same ground as this post: the IBM 650, the SOAP assembler, von Neumann asking why anyone would want more than machine code, and FORTRAN opposed by almost every programmer of the day because it was wasteful, it could not possibly work, and no respectable programmer would use it, only sissies.

His point is not about any single technology. It is about the reaction. Technology changes quickly, people's minds change slowly, and there can be outright hostility to a way of working that asks you to unlearn what you already know. The trap, he says, is the most dangerous thought a creative person can have: that you know what you are doing. Because once you are certain you know what programming is, someone shows you the next thing and it goes right over your head.

He then walks through four directions the 1970s believed programming was heading, none of which happened: direct manipulation instead of code, goals instead of procedures, spatial representations instead of text files, concurrency instead of sequential execution. Same pattern, one more time. Directions that were right about where things were going, dismissed by a field that was sure it knew what it was doing.

## How it actually gets settled

Not by winning the argument. High-level languages did not beat assembly because someone proved the skeptics wrong in a debate. They won because the economics flipped: hardware got cheap and programmers got expensive, and "a bit slower but ten times faster to write" beat "optimal and slow to produce" in every budget that mattered. The same thing is happening here, for the same reason.

So the useful question was never whether generated code is trustworthy. It is the one Thompson's lecture already forced on us: *what can I verify, and what do I have to take on faith?* The answer is not to trust the generator, and not to refuse it. It is to build the verification that makes trust unnecessary where it counts.

Which is why, when I use an AI to write code, I do not believe it. I write a design document first, hand the execution to a bounded agent, and then read the result like I would read a patch from a stranger. Not faith, and not fear. A review.

The compiler earned its trust over twenty years, and we still qualify it before it is allowed inside a cockpit. The generator will earn its own the same way. With tests, and reviews, and time.

Keep reviewing ;)
